# Web UI pages

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This directory is the page part of the web UI, and it connects to a real core. For what the pages look like and why they are designed this way, see `docs/blueprint/web.md`.

The pages are written in plain JavaScript, organized as ES modules, with no framework and no build step. This directory is not part of the repository's Cargo workspace, so the repository-wide checks do not cover it.

## Running

Because a browser can only use WebSocket while the core listens on a local socket, a bridge (`bridge/`) sits between the two. The bridge serves the page files, passes `/ws` to the core, and presents the local token on behalf of the pages.

The core lives in another repository (`miyu-agent/miyu`). Before you run the pages, build the core once in a checkout of the core repository (`cargo build -p miyu`), and replace `<core checkout>` in the commands below with its path. Run:

```sh
# First run: in the root of the core checkout, create the data root skeleton and write the model configuration (etc/config.toml; an existing configuration is not overwritten)
MIYU_DEV_BASE_URL=<address, up to /v1> MIYU_DEV_MODEL=<model> MIYU_DEV_WINDOW=300000 cargo xtask dev-home <separate test directory>
# Go back to the root of this repository
cargo build --manifest-path web-demo/bridge/Cargo.toml
MIYU_HOME=<same directory> MIYU_RESOURCES=<core checkout>/resources MIYU_CORE_BIN=<core checkout>/target/debug/miyu \
  MIYU_DEV_API_KEY=<key> MIYU_DEV_BASE_URL=<address, up to /v1> web-demo/bridge/target/debug/miyu-web-bridge 8766
```

After the bridge starts, it prints a link (`http://127.0.0.1:8766/#k=…`); open it in a browser and you are done. The pass code in the link is only valid for this one run, and without it you cannot connect. The number at the end of the command is the port; if you leave it out, 8765 is used.

Keep the following in mind when you run it:

- The model comes from the configuration in the data root. `dev-home` writes a provider named `dev` whose address refers to the environment variable `MIYU_DEV_BASE_URL` and whose key refers to `MIYU_DEV_API_KEY`; the configuration file does not store the address or the key. When you run `dev-home`, the address must be set; it only checks the form of the address and does not write the address into the file.
- Put the environment variables in front of the command and do not `export` them. Keep the key and the address only in the command, and do not write them into any file.
- When the core is not running, the bridge starts it with `MIYU_CORE_BIN`. Because the core reads environment variables only at the moment it starts, stop the core first after you change them. When the bridge stops, the core does not stop with it.
- The working directory of a new session is the directory the bridge was started in.
- The display names of tools and the one-line summaries of their results on the timeline are read by the bridge according to `MIYU_RESOURCES` (`web.human`). After you change the bridge's code, rebuild and restart the bridge.
- For now the bridge also does a few jobs in place of the core's future web module (see the last section of `docs/blueprint/web.md`): it serves local files and binary data (`/file`, `/blob`, which need the pass code and never serve files from the data root), and it fetches link cards (`web.link_preview`, `/link-image`, which need network access and never fetch internal network addresses).
- Preview workspace: have the AI use `write` to put its output into `artifacts/` under the session's working directory; once it is written, a preview opens on the right automatically (when the window is wide enough).

## Testing

The pure-logic parts of the pages have tests. The tests take event samples from the repository as input and do not need a browser. They cover turning events into items, the segments and text of the timeline, diffs, one entry in the left column, the line under the input box, how numbers are written, Markdown parsing and highlighting in answers, what goes into the preview workspace, and media cards.

Run:

```sh
MIYU_RESOURCES=<core checkout>/resources node --test 'web-demo/tests/**/*.test.js'
cargo clippy --manifest-path web-demo/bridge/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path web-demo/bridge/Cargo.toml
```

Node is only used during development; the pages themselves do not need Node.

## Vendored libraries

The libraries below are used to display Markdown in answers and to generate QR codes. They are all copied in unchanged; the pages only load them locally and never connect to outside addresses.

| Library | Version | License | What was copied | How it is used |
|---|---|---|---|---|
| [Prism](https://prismjs.com) | 1.29.0 | MIT | `vendor/prism/prism.min.js`: one file combining the few languages needed; the top of the file explains how to rebuild it | Loaded with `data-manual`; only `Prism.tokenize` is called (`src/markdown/highlight.js`) |
| [KaTeX](https://katex.org) | 0.18.4 | The code is under MIT (`vendor/katex/LICENSE`), the fonts under SIL OFL 1.1 (`vendor/katex/fonts/OFL.txt`) | `vendor/katex/katex.min.js`, `vendor/katex/katex.min.css`, `vendor/katex/fonts/*.woff2` | Calls `katex.render` (`src/markdown/math.js`) |
| [qrcode-generator](https://github.com/kazuhikoarase/qrcode-generator) | 2.0.4 | MIT (`src/lib/qr/vendor/LICENSE`, taken from the upstream repository) | `dist/qrcode.mjs` from the npm package, placed in `src/lib/qr/vendor/` | Calls `qrcode(0, 'M')`, `addData` and `isDark` (`src/lib/qr/index.js`) to generate the QR code for the local network address |

> qrcode-generator lives under `src/lib/` rather than `vendor/` because packages in the pages can only `import` files in `src/lib/`; material-color-utilities is handled the same way.
